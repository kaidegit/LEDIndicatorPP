# ledip_tester 设计与实施交接

日期：2026-11-11

本文记录已讨论确认的测试工具方案，并为后续实施 agent 提供工作范围、设计约束和验收标准。当前交付仅为文档，尚未实施测试工具，也未通过运行测试确认下文列出的代码风险。

## 1. 目标与已确认决策

项目名称为 **ledip_tester**，用于测试本仓库 LEDIndicatorPP 组件。

- 只关注 WASM 环境，不集成 MCU、烧录、串口或目标板资源分析。
- 将真实 C++ 组件与驱动编译为 WASM，不用 JavaScript 重写组件充当被测对象。
- 无头模式使用 Node.js 直接运行 WASM，不依赖浏览器、Playwright 或本地服务器。
- Web 模式使用浏览器 Web Worker 运行 WASM，提供直观的 LED、时间线和指标展示。
- 两种模式共用同一份 WASM、场景协议、测试引擎、断言和结果协议。
- 使用虚拟时间实现确定性测试，不以真实等待驱动功能测试。
- 被抢占的低优先级 pattern **继续在后台推进时间和步骤**，可以自行结束；只有当前最高优先级 pattern 控制实际输出。
- 组件动态内存使用可配置固定池和 TLSF，支持统计和分配失败注入，池耗尽时不得回退到默认堆。
- 报告 WASM 内存、性能和产物体积；不得将其标成实测 MCU SRAM、Flash 或速度。

## 2. 范围

需要覆盖：

1. 功能与时序正确性，包括优先级、抢占、恢复、重复操作和边界输入。
2. 动态内存预算、峰值、分配行为、碎片、释放和内存不足行为。
3. WASM 操作耗时及随场景规模增长的趋势。
4. WASM 发布产物体积及固定配置下的版本增量。
5. AI 可自动运行、读取结果、复现和缩减失败场景。
6. 人可以在 Web 中编辑场景、单步执行、观察轨迹并定位失败。

不在首版范围：MCU 数据、真实 GPIO、电气时序、硬实时保证、真实 RTOS 并发正确性、数据库、云服务、浏览器自动化运行依赖、完整 WASM 快照恢复。不得为测试方便顺带实现 PWM、WS2812 等组件新功能。

## 3. 总体架构

```text
CLI 参数 / 文件 / stdin                  Web 场景编辑 / 结果展示
          |                                      |
Node 主线程：文件、报告、超时           浏览器主线程：界面、超时
          |                                      |
Node Worker Threads                      Web Worker
          +------------------+-------------------+
                             |
                 TypeScript 共享测试引擎
              场景调度 / 断言 / 参考模型 / 随机测试
                             |
                       WASM C ABI
                             |
                真实 LEDIndicator + 实际驱动
                   |           |          |
                 虚拟时钟    TLSF 固定池   输出记录
```

共享引擎不依赖 React、DOM 或 Node 文件 API。宿主适配层只处理加载、单调计时、消息、取消、文件和产物保存。Node 与浏览器分别使用 Worker 隔离执行；监控超时的主体必须在执行 Worker 外部，能够终止无限循环。

每个 Worker 同时运行一个场景实例。默认独立 WASM 实例隔离测试；内存压力测试在同一实例中执行连续操作。检查销毁后残留分配，再销毁实例，不得用重置池掩盖泄漏。

## 6. C++ 与 WASM 边界

采用小型 C ABI，传递句柄、标量和连续数据缓冲区。接口职责示意如下，名称与签名在实施时确定：

```text
create / destroy
add_pattern / start / stop
set_time / update / run_batch
read_events / read_state / read_memory_stats
configure_allocation_failure
```

JSON 解析、断言和报告生成放在 TypeScript。WASM 中不引入大型 JSON 或测试框架。提供有界的命令、事件和状态缓冲区，明确所有权、有效期、容量和错误码。事件缓冲溢出必须报告为结果不完整或执行失败，不能静默丢失。

当前 `GetTime()` 依赖 RT-Thread/FreeRTOS，需加入最小时间注入接缝，保留原平台默认行为。组件头文件中的 `magic_enum.hpp` 依赖也需要明确获取方式与版本，不应假定系统已有。

允许增加必要的只读状态观测接缝，用于调试步骤索引、累计时间和活动列表。不能仅依赖内部状态判断正确性，主要断言必须覆盖外部驱动输出。调试观测应可关闭。

测试时可使用：

- 记录型 LEDDriver：记录状态、亮度、颜色、索引颜色、清空等接口调用。
- 实际 GPIO/RGB GPIO 驱动：捕获真实驱动发出的引脚电平与掩码。

页面应区分驱动请求与实际引脚输出。例如当前 RGB GPIO `setColor()` 只更新缓存，`ON` 才写引脚，不能直接把颜色请求当作实际亮灯。

## 7. 时间、场景与行为契约

### 7.1 场景协议

场景至少包含：协议版本、用例 ID、驱动类型、内存配置、pattern 定义、操作序列、断言、虚拟运行预算、真实超时预算、随机种子（如适用）。

操作包括注册/替换 pattern、start、stop、推进时间和 update。场景应显式表达 update 调度，区分“时间变化”和“执行更新”，支持固定周期、不规则周期、同一时刻重复更新和大跨度跳时。

同一时间点的操作按输入数组顺序执行，不依赖事件循环排序。内部场景时间可以单调增长，传入组件时按 uint32_t 毫秒映射，以测试回绕。虚拟时间和真实耗时计时完全分离。

Schema 校验错误必须给出字段路径与原因。正常输入验证与鲁棒性测试分开：前者拒绝格式错误；后者允许有意构造空步骤等组件边界输入，避免在适配层把所有风险挡掉。

### 7.2 已确定语义

- 数值更小的优先级先执行，匹配当前组件排序方式。
- 抢占期间，低优先级 pattern 继续推进，可在后台遇到 STOP 并结束。
- 只有最高优先级活动 pattern 产生实际控制输出。
- 高优先级退出后，恢复仍存活的最高优先级 pattern 当前应有的输出。
- 相同输入、种子、构建与调度规则应产生相同功能结果；真实耗时不要求逐次相同。

### 7.3 实施前需明确记录的细节

以下未在讨论中逐项定案，实施 agent 应先对照代码建立语义表。普通细节可提出合理默认；会改变既有用户可见行为的歧义应向用户确认，不得悄悄用现有实现作为正确性标准。

- start 到首次 update 之间如何计时，重复 start 如何重置。
- 所有 pattern 结束后是保持最后输出还是关灯。
- 抢占恢复时颜色、亮灭、亮度、CLEAR 等状态的完整恢复规则。
- 运行中替换 pattern 的步骤索引与时间如何处理。
- 空 pattern、首步 STOP、缺少终止步骤、零时长循环如何拒绝或终止。
- 分配失败的返回、异常和状态一致性契约。
- 暂未支持的步骤/驱动能力如何标为 unsupported。

参考模型依据明确的行为契约实现，不逐句翻译 C++ 算法。确定性断言、独立参考模型、不变量检查三者结合。

## 8. 固定池与内存统计

组件对象、pattern 容器、map/list/vector 节点及驱动对象等动态分配进入 TLSF 池。JSON、报告、轨迹和测试框架分配不计入组件池。必须审计实际使用的分配入口，覆盖相应 new/delete、数组、对齐、nothrow 及 malloc 系列路径，遵守 C++ 分配失败语义。

不能仅包装一个分配函数就宣称完整覆盖。使用已知分配的验证场景检查统计，并明确运行库与适配层的归属。禁止池耗尽后偷偷回退。TLSF 控制结构、对齐和块管理成本需计入或单独披露。

至少报告：

- 总池容量、可用初始容量、分配器固定成本。
- 当前与峰值请求字节、当前与峰值实际池占用。
- 分配/释放/失败次数、当前存活块数。
- 空闲总量、最大空闲块、明确公式的碎片指标。
- 组件销毁后的残留块与字节。
- 失败分配的序号、请求大小和所在场景操作。

空闲块遍历及碎片快照属于诊断操作，不放入性能测量热路径。可在创建、注册、启动、更新、停止、销毁等阶段采集差值。

独立报告静态区、TLSF 预留池、线性栈预留量与可测高水位、WASM 线性内存容量。池位于静态区时不可重复相加。未知或尚未可靠测得的指标显示 unavailable，不填零。浏览器/Node/JIT 本身的内存不算组件 RAM。

支持池容量扫描和第 N 次分配失败注入；“最小容量”仅表示指定配置、指定场景下已验证的容量，并报告搜索方法和粒度。

自定义池不自动获得完整的小块 ASan 检查能力。内存诊断可采用红区、释放填充、TLSF 一致性检查及显式 sanitizer 标记；未覆盖能力必须如实标注。

## 9. 测试矩阵

| 类别 | 重点用例 |
| --- | --- |
| 基础行为 | HOLD、LOOP、STOP、启动停止、重复启动、未注册类型 |
| 优先级 | 多级抢占、后台推进、后台结束、高优先级结束后的恢复 |
| 时序 | 边界前后 1 ms、不规则 update、大跨度跨步、uint32 回绕 |
| 非法与极端输入 | 空步骤、首步 STOP、末尾无终止、零时长循环、极大时长 |
| 动态修改 | 运行中替换、更短 pattern、重复注册 |
| 驱动 | 有效电平、RGB 缓存、引脚掩码、无驱动、能力不支持 |
| 内存 | 生命周期释放、反复替换、池耗尽、第 N 次分配失败、碎片压力 |
| 规模与性能 | pattern 数、活动数、步骤数、跨步数、长时间操作序列 |
| 随机测试 | 固定种子、操作序列、不变量、参考模型比较、失败缩减 |

静态阅读发现的重点风险：步骤索引访问缺少边界检查；零时长循环可能卡住；活动 pattern 替换为短列表可能使旧索引失效；抢占恢复主要缓存颜色。它们是待验证风险，不是已经测试确认的结论。

当前 HSV 没有实际执行行为，BREATHE 没有完整渐变实现。报告区分 pass、fail、unsupported、skipped 和执行错误，不将“未崩溃”视作支持功能。

测试工具不得用步数截断将被测死循环伪装为通过；超出预算需明确失败。锁回调配对可以测试，但不宣称由此验证真实多线程竞争。

## 10. 性能与体积

### 10.1 构建配置

- Debug：状态观测、完整轨迹、功能断言。
- Memory-check：红区、分配失败、内存校验，按能力启用 sanitizer。
- Release：优化构建，关闭详细轨迹与昂贵诊断，用于性能。
- Size：固定优化、固定导出根、去调试信息，用于体积。

不同配置的指标不得混为同一基线。异常策略、TLSF 版本、优化级别及 LTO 设置必须记录。

### 10.2 性能

预热后重复批量测量，报告中位数、分位数、样本数和批量大小。组件操作批量在 WASM 内执行，减少跨界调用干扰；同时单独提供 JS→WASM 端到端指标。不得将单次 JS 调用耗时标为纯 C++ 执行耗时。

防止编译器优化掉工作，保留可验证结果。性能基准串行执行，不同时刷新动画或扫描 TLSF 块。报告 Node/浏览器、运行时版本、主机环境、编译器和构建参数。Node 与浏览器分别建立性能基线，不要求数值相同。

### 10.3 体积

报告 `.wasm` 文件总大小、Code section、Data section，以及可选的 JS 胶水大小。使用可比的空基线和组件构建报告增量，保留相同工具链、导出策略和配置，标明 TLSF/适配层成本。

Data section 的文件体积与运行时 RAM 占用是不同口径。初始化零数据未必按运行时大小出现在文件中。不要把 `.wasm` 总大小直接叫 MCU Flash；页面可解释为 WASM 代码/存储体积。

体积由构建脚本分析产物并生成报告；Web 负责读取展示，不需要浏览器在线编译。

## 11. CLI、报告与可复现性

命令示意（最终帮助文本与实现保持一致）：

```sh
ledip_tester run --scenario case.json --format json
ledip_tester run --scenario - --format json
ledip_tester suite --name regression
ledip_tester fuzz --seed 12345 --iterations 10000 --heap-size 32KiB
ledip_tester bench --profile release
ledip_tester size --profile size
ledip_tester serve
```

复杂输入从文件/stdin 读取，参数用于选择和覆盖。默认无交互。JSON 模式 stdout 只输出协议数据，日志写 stderr。约定稳定退出码，例如 0 通过、1 测试/预算失败、2 输入错误、3 工具或执行异常；最终枚举需文档化。

结果至少包含协议版本、用例 ID、状态、构建标识/源码版本、环境、有效配置、种子、断言结果、指标、产物路径和复现信息。失败包含首次偏差的虚拟时间、操作索引、预期/实际值。明确 timeout、trap、OOM、断言失败、轨迹溢出等原因。

复现包保存原场景、有效配置、轨迹和构建信息。随机失败缩减得到的新场景必须再次运行确认。不要只保存种子而遗漏生成器版本。

功能跨宿主对比仅比较确定性的语义字段，排除真实耗时、路径等宿主差异字段。

## 12. Web 交互

- 场景选择、表单和 JSON 编辑、导入导出。
- LED 预览，区分请求状态、缓存状态和实际引脚输出。
- 多 pattern 时间线、当前步骤、优先级与抢占关系。
- 暂停、单步、推进指定时间、播放速度控制。
- 断言列表，定位首次偏差并联动时间线。
- 内存曲线、阶段分配统计、按需 TLSF 块分布。
- 性能与体积报告，支持基线比较。
- 加载 CLI 导出的复现包并重放。

向后拖动时间线默认回放已有轨迹；从过去继续执行时重新初始化并确定性重放，不做内存快照恢复。超时/崩溃不应卡住 UI，终止后可以运行下一用例。

## 13. 实施阶段与验收

### 阶段 A：最小纵向闭环

独立 WASM 构建、时间接缝、基础驱动捕获、场景协议、共享引擎、Node Worker CLI 和最小 Web Worker 页面。

验收：同一基础场景在 CLI/Web 得到一致输出与断言；CLI 不启动浏览器或服务器；WASM 死循环可被外部超时终止；不破坏已有平台集成。

### 阶段 B：内存可观测与回归测试

接入 TLSF、分配归属、统计、生命周期校验和失败注入；建立优先级/抢占/时序/边界回归集。

验收：已知分配场景的计数与字节正确；池耗尽不回退；残留分配可检出；碎片报告口径明确；未支持行为不假报通过。

### 阶段 C：可视化与失败复现

完整时间线、单步、轨迹导入、内存图、失败定位；固定种子随机测试与失败缩减。

验收：CLI 失败包可在 Web 重放到同一首次偏差；缩减结果保持失败；界面区分请求与实际输出。

### 阶段 D：性能与体积基线

独立构建配置、批量基准、规模矩阵、体积 section 分析、基线比较。

验收：报告包含环境与构建信息；测量不包含详细轨迹/UI 成本；Node/Web 基线分开；体积不混入调试信息；未知指标不假报零。

每阶段提供可运行命令、实际验证结果和剩余限制，不仅交付目录与接口占位。可以发现并修复组件 bug，但应先保留失败复现用例，修复与测试工具基础设施分开说明；涉及未定行为契约时先确认。

## 14. 给实施 agent 的开始步骤

1. 阅读本文件及仓库当前源码，检查适用的 AGENTS.md 和工作区改动。
2. 列出当前编译依赖、最小时间接缝、分配覆盖方案与行为契约表。
3. 先验证 Node 与浏览器加载同一份 WASM 的最小闭环，再扩展功能。
4. 保留现有 ESP-IDF/RT-Thread 接入路径，避免将测试依赖带入发布组件。
5. 按阶段验收，报告已运行的检查和真实限制；不要宣称测试证明完全不存在 bug。
